- 2026-09-17 — [Build Slice] 16. Heading outline content: replaced `OutlineRail`'s placeholder body with the open document's real headings, and made clicking one scroll the preview to that section — the first half of ADR-0018's outline work (extraction + jump-to-section; scroll-spy and the breadcrumb's in-document segment are a deliberate follow-on, named below).

  **What shipped.** `preview/headings.ts` — `extractHeadings(content)` parses the raw Markdown with `unified`/`remark-parse`/`remark-gfm` (the same parser react-markdown builds internally), walks the mdast tree for `heading` nodes via `unist-util-visit`, and slugs each one's plain text (via `mdast-util-to-string`, so inline formatting like `` `code` ``/`**bold**`/links is stripped before slugging) with a fresh `github-slugger` instance per call, in document order.   **New dependencies**, versions read back from `package.json` after installing at `@latest` per the Working Agreement: `rehype-slug` `^6.0.0`, `github-slugger` `^2.0.0`, `unified` `^11.0.5`, `remark-parse` `^11.0.0`, `mdast-util-to-string` `^4.0.0`, `unist-util-visit` `^5.1.0`, `@types/mdast` `^4.0.4`. The four `unified`-ecosystem packages were already present as transitive dependencies of `react-markdown`/`remark-gfm` at these exact resolved versions; declared directly since application code (`headings.ts`) now imports them by name rather than relying on npm's flattening to keep providing them.

  **Bug caught by a test, not by eye: the id-mismatch.** `rehype-sanitize`'s default (GitHub) schema sets `clobberPrefix: 'user-content-'`, which prefixes every sanitized `id` — including the ones `rehype-slug` assigns — to stop a heading id from clobbering a same-named DOM global (e.g. `document.getElementById`/`window` property collisions from attacker-controlled raw HTML). `headings.ts`'s independently-computed slugs didn't carry that prefix, so a click would have looked up the wrong element and silently done nothing — not caught by `npm run dev`'s visual smoke check, but caught immediately by a new DocumentPreview test asserting id parity between `extractHeadings` output and the actual rendered DOM. Fixed by extracting `sanitizeSchema` (previously inline in `DocumentPreview.tsx`) into its own module, `preview/sanitizeSchema.ts`, which also exports `HEADING_ID_PREFIX = sanitizeSchema.clobberPrefix ?? ''` as the single source of truth both `DocumentPreview.tsx` and `headings.ts` read from. The extraction was also required by ESLint's `react-refresh/only-export-components` rule, which forbids a component file from exporting a non-component value.

  **Scope held.** No scroll-spy (highlighting the section currently in view while scrolling) and no breadcrumb in-document segment — both need continuous scroll-position tracking against this same heading list and are a natural, separate follow-on now that the heading data exists. No setext-heading (`Title\n===`) support — ATX (`#`) headings cover the realistic corpus; can add later if it matters. No mockup "Section X of Y" footer counter.

Validated the premise first: no ADR, no `architecture.md` §2 row, no shape Decision covered CSS, theming, icons or fonts. Confirmed genuinely open.

  **What was already leaking in.** Slice 3 shipped the `electron-vite` template's `base.css` unchanged — 67 lines of `--ev-c-*` variables with **no light palette at all**, and `main.css` already consumed two of them. Its reset also carried `ul { list-style: none }` and a blanket `font-weight: normal`, which would have stripped list markers and heading weights out of every rendered Markdown document. Not a decision anyone made; a default inherited from a scaffold. That is the specific drift this unit stopped.

  **Decision: semantic CSS custom properties + plain CSS/CSS Modules.** Rejected Tailwind + shadcn (utility classes in JSX work against the read-every-line mandate; adds a build plugin; `prose` would be fought over Mermaid and heading anchors), a component library (Fluent/Mantine/MUI — a reader app is overwhelmingly custom surfaces, so it means adopting a styling engine to use a fraction of it), and runtime CSS-in-JS. Rationale and the revisit path are in ADR-0020. The choice is deliberately **not** a dead end: Tailwind consumes CSS custom properties directly, so adopting it later reuses `theme.css` rather than replacing it.

  **The argument that actually decided it** was structural, not preferential: there are two styling domains, and the document surface is HTML emitted by `react-markdown` that **cannot carry classes**. It needs a scoped stylesheet under every option, so no framework removes that work — which collapses most of the case for adding one at this size.

  **"Follows the OS" turned out to need no IPC.** Electron's `nativeTheme.themeSource` defaults to `'system'`, so Chromium already resolves `prefers-color-scheme` from Windows. The originally proposed `nativeTheme` → IPC → `data-theme` plumbing was dropped as unnecessary: dark is one `@media` block. The only main-process change is `BrowserWindow.backgroundColor` from `nativeTheme.shouldUseDarkColors`, plus a `nativeTheme.on('updated')` handler, so the window does not paint the wrong theme before the stylesheet loads or during a resize. No preload surface, no renderer state, no config key. Per the maintainer's direction, v0.1 has **no in-app theme picker** — `product.md` §10's `"theme"` key is forward-looking and v0.1 behaves as though it is always `"system"`; consistent with ADR-0013 cutting the settings UI.

  **Contrast was computed, not claimed.** A script parsed the hex values out of `theme.css` and checked 17 foreground/background pairs per theme. The first run **failed two**: `--color-border-strong` at 1.60:1 (light) and 2.05:1 (dark), against the 3:1 WCAG 1.4.11 floor for control boundaries — it is the input-outline and scrollbar-thumb token. Both values were changed (`#c8cdd4` → `#878d96`, `#454c56` → `#656d78`); 34/34 now pass. Worth recording that the checker itself was wrong on its first run too — it split light from dark on `indexOf('prefers-color-scheme: dark')`, which matched the file's own header comment and put every token in the dark bucket. Fixed to match `@media (…)` before any token value was trusted. A broken oracle would have reported a clean sweep.

Rewrote `base.css` onto tokens with a reset that leaves list markers and heading weights alone. `main.css` moved to semantic tokens and layout constants. `src/main/index.ts` gained `windowBackground()`. Docs: ADR-0020, ADR index row + next-number bump to 0021, four rows in `architecture.md` §2 with a dated "Added" note.

## Skill Feedback

- **The version-pinning mechanism was spelled out explicitly in this shape (Working Agreement, and again in the 2026-09-13 hardening Pass) and it still nearly slipped.** While editing `package.json` to add vitest/testing-library as devDependencies, the first draft hand-typed plausible-looking version numbers before running any install — caught on self-review before the install ran, not by an external check. The habit of writing a version string as part of writing a `dependencies` object line is strong enough to survive an explicit standing instruction. No skill change proposed yet — one catch isn't a pattern — but if it recurs, the fix is probably procedural (write the bare package name, run `npm install --save-dev <name>@latest`, let npm fill in the field) rather than another sentence of instruction.

- **The skill has a closing procedure but nothing that prompts compaction during a long run.** `shape.md` reached 71.3KB / 262 lines while its own template header said "current state only." Four separate symptoms — the file becoming a second log, `Status: Draft` surviving a shipped MVP, `Current unit` holding eight completed units, and `NEXT.md` going eight days stale — are all the same missing step, and none of them tripped anything. The end-of-pass checklist in `references/capture-formats.md` does say "Reset `Current unit`" and "Update `Resume next session`", and both were being done in the sense of _rewriting_ those sections each pass; what was never done was _shrinking_ them, because each pass appended its own "On top of that…" paragraph to a section that only ever grew. Suggested change: the checklist's step 3 should say reset means replace, not append, and the **still right?** check (which already asks "what has been added that could now be deleted") should apply to the shape file itself, not only to the design. A size or age trigger would work too — but the cheaper fix is wording, since the step already exists and was being read as satisfied.

- **Per-slice manual checks never re-examine a boundary an earlier slice claimed.** A code review on 2026-09-21 found 14 security/correctness items in shipped MVP code, every slice of which had passed its own manual check. The sharpest one: a main-process function's docstring, an IPC handler comment, and a log entry from the Slice 19 fix all assert that the trusted-root boundary is "enforced in the main process rather than trusted from the renderer" — and it is not, because the root path it validates against is supplied by the renderer. The Slice 19 reasoning was internally consistent and wrong, and three rounds of manual checks after it had no reason to look. This is not an argument for heavier per-slice validation; it is an argument that a shape's _close_ should include one review pass across the accumulated surface, distinct from the per-unit checks. Suggested change: add an audit step to the closing procedure, in the same spirit as the loop's existing step-3 "external standards" check but scoped to the whole shape rather than one unit.
