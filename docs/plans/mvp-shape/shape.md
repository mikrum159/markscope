# MarkScope MVP Shape

Status: **Closed** — 2026-09-21. See the [closure summary](log.md#closure-summary) for what shipped, what was deferred, and where it went.

Successor: [MarkScope public release shape](../public-release-shape/shape.md).

This file holds the decisions, constraints and open questions that outlived the MVP. The build history — 65 dated units, oldest first — lives in [log.md](log.md) and is not summarized here.

## Intent

A standalone Windows Markdown reader over multiple local folders — original hierarchy preserved, non-Markdown files and empty branches filtered out, with comfortable reading and in-document navigation. The repo had ~20 planning documents written for a different project (agent-driven build, dual-platform, Tauri/Rust) and zero code; this shape reconciled that and carried the build through to a validated installer.

## Working Agreement

Carried forward into the successor shape unless noted.

- Human-driven. The maintainer works in C# and TypeScript and must be able to read and own every line. Readability beats cleverness; no code that can't be explained in review.
- Every unit's Validation is a **command**, never a claim (`quality.md` §4 done-condition rule).
- **Never commit or push.** Show the diff and stop; the maintainer commits (`AGENTS.md`, and the skill's default).
- **Dependency versions come from the registry, never from memory or from the imported documents.** The mechanism, not just the principle: install with `@latest` (or check `npm view <pkg> version` first), then read the _resolved_ versions back out of `package.json` / the lockfile and record those in the capture. Commit the lockfile. A version number written from recall is a guess even when it looks right.
- Per `CONTRIBUTING.md`: record exact revision, commands, outcomes, and platform. Distinguish "not run" from "passed".
- **When a unit changes how the project is built, run or verified, update `AGENTS.md` in the same unit.** A unit can pass its own goal and still leave that section stale — check it every time the build changes.
- Shape files here are committed with the repo (unlike the skill default), since `docs/` is the project's documentation home.

## Current Shape

### Current understanding

The MVP shipped. All 21 numbered slices plus the packaging unit are built, validated, manual-check closed and committed on the `mvp-shape` branch (32 commits ahead of `main`, unmerged). `npm run typecheck && npm run lint && npm test` passes 134/134; `npm run dist` produces a working NSIS installer, manual check closed 2026-09-21.

What the app does today: multi-root Markdown browsing with preserved hierarchy and pruned empty branches, tabbed reading with a transient preview tab, per-tab scroll memory surviving restart, a heading outline rail with scroll-spy and jump-to-section, a breadcrumb with an in-document segment, Mermaid diagrams and document-relative images, SQLite FTS5 full-text search behind Quick Open, drag-reorderable roots, persisted window state, and a real theme picker. No network surface of any kind.

### Decisions

Source noted per entry. Anything inherited from a document is a claim, not a verified fact.

- **Electron + React + TypeScript**, not Tauri v2 + Rust. _Source: developer, planning session._ Supersedes ADR-0001. Costs ~150MB installer, ~250MB idle RAM, ~1.2s cold start; buys one language end-to-end that the owner can maintain. Claimed to stay inside `quality.md` §6's 2s startup target — the target itself is unverified, see Constraints.
- **SQLite FTS5 via `better-sqlite3`**, not Tantivy. _Source: developer, planning session; already the documented fallback in ADR-0006._ Weaker ranking than Tantivy, imperceptible at a few thousand docs.
- **Windows-only v0.1.** _Source: developer, this session and planning session._ Supersedes ADR-0010. No macOS artifact, no CI matrix, no DMG.
- **Deterministic heading outline in v0.1; AI summaries in v0.2**, lazy-on-first-open and cached by content hash. _Source: developer, planning session._ Supersedes ADR-0012. v0.1 has **no network surface at all**. The v0.2 caching model deliberately supersedes `architecture.md` §3 principle 8 ("network only on explicit user action") and needs its own ADR rather than a silent edit.
- **All roots durable. Ephemeral roots and the CLI entry point are dropped, not merely deferred.** _Source: developer, 2026-09-13, answering Open question 1 directly._ Defers ADR-0011 and rejects its premise: CLI triage is **not** how the maintainer works, so `product.md` §7.1's "headline workflow" framing is wrong and gets rewritten in Unit 2, not preserved as a deferred feature. Removes a second persistence model from workspace, catalog, search, watcher and tabs.
- **Automated doc triage is out of MarkScope's scope, possibly a different project entirely.** _Source: developer, 2026-09-13._ MarkScope's job is reading folders of Markdown, including already-triaged ones — which needs no special support, because a triaged folder is just a folder. Explicitly **not** being designed for now; revisit only if that other project becomes real.
- **shape-dd `log.md` is the only build journal.** _Source: developer, planning session._ Supersedes ADR-0014, whose premise (agent-driven build as portfolio artifact) no longer holds. Also retires `product.md` §2 and §14 positioning.
- ADR-0003/0004/0005/0007/0008/0013 stand as written; **ADR-0009 stands with a revision** — GitHub Releases yes, updater artifacts no, self-update out of v0.1. _Source: reconfirmed on the record 2026-09-13, ADR index._ ADR-0005 was added to the reconfirm set because ADR-0017 puts the FTS5 index in that database.
- All fourteen imported ADRs now have a current applicability label; none remain "pending reconfirmation". _Source: `docs/adr/README.md`, 2026-09-13._ The reversals above are no longer shape-only claims — each has an ADR with its rationale and rejected alternatives.
- **Styling is semantic CSS custom properties + plain CSS/CSS Modules; light/dark follows the OS only in v0.1.** _Source: developer, 2026-09-13, answering a gap they raised; recorded as [ADR-0020](../../adr/0020-css-design-tokens-for-styling-and-theming.md)._ Supersedes nothing — ADR-0015 fixed the stack and never covered styling, and the scaffold had been silently running on the `electron-vite` template's dark-only palette. `theme.css` is the token source of truth. Rejected Tailwind/shadcn, a component library, and CSS-in-JS; the deciding argument was that `react-markdown` output cannot carry classes, so the document surface needs hand-written scoped CSS under every option. No in-app theme picker, no config override, no icon or font dependency yet. Contrast is a token constraint (AA in both themes), verified by computation rather than asserted.
- Shape lives at `docs/plans/mvp-shape/`. _Source: agent, routine choice_ — matches the source plan and the repo's existing plans home.
- **`product.md` §10's built-in `exclude` list gained `**/ignored/**`.** _Source: agent, Slice 5 agreement, 2026-09-13._ Resolves a gap the Slice 4 log entry named but left open: the `test-docs/ignored/` fixture folder was documented as "under a built-in ignore pattern" but no pattern actually matched a folder literally named `ignored`. Extended the pattern list rather than rename the already-validated fixture.
- **`electron-vite` (react-ts template) is the scaffolding tool**, not Electron Forge's Vite plugin or a hand-rolled Vite config. _Source: agent, Slice 3 agreement, 2026-09-13, checked live rather than from memory._ Electron Forge's Vite plugin graduated out of experimental status only two days before this decision (2026-09-11); `electron-vite` is the established, actively maintained tool built specifically to separate main/preload/renderer, and its template produces exactly `architecture.md` §5's layout without modification. Does not supersede an ADR — ADR-0015 fixed the stack, not the wiring, and this decision fills that gap without contradicting it.
- **Persistence's `roots`/`expanded_folders` schema (`rootsRepository.ts`) is purpose-built for this unit, not `search-and-catalog.md` §5's `trusted_roots`/`folders`/`documents`/`tabs` tables.** _Source: agent, persistence unit agreement, 2026-09-15._ Different concern: this schema holds UI session state (which roots are open, in what order, collapsed/expanded), the catalog schema holds indexed document content keyed by a generated `root_id`. Same database file (`app.getPath('userData')/markscope.db`), so the later search unit can extend it, but reconciling the two schemas (e.g., whether `roots` gains a generated `id` for `documents.root_id` to reference) is that unit's decision, not pre-solved here.
- **Tabs' `tabs`/`active_tab` schema (`rootsRepository.ts`) is likewise purpose-built, not `search-and-catalog.md` §5's `tabs` table.** _Source: agent, tabs unit agreement, 2026-09-15._ Same reasoning as the roots/expanded_folders decision above: session state (`root_path`/`relative_path`/`name`/`position`, keyed the same way `roots` already is), not the catalog's `document_id`-keyed version. No pinning field, since v1 has no pinning.
- **`lucide-react` is the app's icon library.** _Source: maintainer, design-reconciliation Decision Slice, 2026-09-16._ Fulfills the deferred half of [ADR-0020](../../adr/0020-css-design-tokens-for-styling-and-theming.md)'s icon line (that ADR named `lucide-react` as the intended choice back on 2026-09-13, deferred until a slice actually needed one — see the ADR's dated addendum). Zero transitive dependencies (`npm ls lucide-react` confirmed), so it doesn't touch the `mermaid`/`chevrotain`/`lodash-es` risk already tracked below. Icon sizes/stroke-widths follow `docs/specs/design-v1.html`'s own values exactly (14/15px, 1.8 stroke-width for folder/file icons; 16px/default-2 elsewhere) rather than a house rule.
- **Custom title bar: not built.** _Source: maintainer, design-reconciliation Decision Slice, 2026-09-16._ `design-v1.html`'s mockup draws its own title bar; the app keeps the native Windows one. No `frame`/`titleBarStyle` change to `main/index.ts`.
- **Settings and Search get real entry points (a tab and a modal respectively), not dead rail icons — but no real functionality.** _Source: maintainer, 2026-09-16._ Reverses the "no settings UI" Candidate Slices line only for a _navigable shell_: clicking Settings shows a placeholder settings section list and content pane; clicking Search opens a placeholder Quick Open modal. `product.md`/ADR-0013's "no settings UI in v1" still holds for the actual feature — placeholder text was used instead of copying the mockup's theme-picker cards/toggles verbatim, since a control that visibly does nothing (a toggle that doesn't toggle) is worse than no control. Real settings and real search remain later work (v2 / the "search" candidate slice).
  - **Update, 2026-09-19 — partially reversed.** _Source: maintainer._ Settings → **Appearance** is now real: a Follow system/Light/Dark theme picker, persisted (new `settings` table, `rootsRepository.ts`) and applied via `nativeTheme.themeSource` — see [ADR-0020](../../adr/0020-css-design-tokens-for-styling-and-theming.md)'s dated addendum for the mechanism. Settings → **About** is also real, a short static description of what MarkScope is — no persistence, no controls. The other three nav sections (Folders, Search & index, Keyboard shortcuts) stay exactly as before: visible in the nav, disabled, no content — the maintainer's explicit choice (asked as a fork) over dropping them from the nav until built, so the section list's shape doesn't change twice. `product.md`/ADR-0013's "no settings UI" still holds for everything except these two sections.
- **Packaging (v0.1) targets "just me for now": no code signing, no auto-update, no CI/publish automation.** _Source: maintainer, 2026-09-19, answering the fork asked directly before scoping the packaging unit._ Confirms rather than reopens ADR-0009's existing "installer ships, signing/`electron-updater` deferred" call. Windows SmartScreen will show an "unknown publisher" warning on first run of the unsigned installer — accepted as fine for personal use. If this changes (the app is shared with others), signing needs a certificate and reopens that ADR's call; tracked as Open question 2, not resolved by this decision.
- **NSIS installer, per-user, wizard-mode (not one-click).** _Source: agent, packaging unit agreement, 2026-09-19._ Matches the already-recorded precedent in the superseded `packaging-and-releases.md` ("v0.1 ships an NSIS installer") rather than opening a new format fork. `oneClick: false`/`allowToChangeInstallationDirectory: true` overrides electron-builder's actual default (a silent install-and-launch with no wizard) — a routine reversible setup choice, not asked as a fork.
- **Heading extraction re-parses the raw Markdown with `unified`/`remark-parse`/`remark-gfm` rather than reading `DocumentPreview`'s already-rendered DOM.** _Source: agent, Slice 16 agreement, 2026-09-17._ Keeps `OutlineRail`'s content available independent of whether/when the preview has rendered, and avoids a DOM-scraping dependency between two components. The cost is a second parse pass per document open; not measured, and not expected to matter until it's shown to (see the existing large-document-preview Risk, which already tracks parse/render cost at this document-size profile). IDs are kept in sync with the real render via a shared `HEADING_ID_PREFIX` constant (`preview/sanitizeSchema.ts`) and a regression test asserting id parity, rather than by trusting the two implementations to stay coincidentally aligned.
- **Per-tab scroll position is persisted across restart (`tabs` table gains a column), not renderer-session-only.** _Source: maintainer, 2026-09-17, answering the durability fork directly._ Consistent with how `roots`/`expanded_folders`/`tabs`/`active_tab` already survive a restart (Slices 10-11); trades a bigger unit (schema column, IPC write path) for that consistency rather than the smaller renderer-only alternative.
- **Search's catalog schema extends `search-and-catalog.md` §5's `documents` table (plus its `documents_fts` FTS5 virtual table from §7), not a third purpose-built schema.** _Source: maintainer, Decision Slice, 2026-09-17, answering the fork named when Slice 18/19 closed._ Reverses the default this shape had been leaning on for `roots`/`tabs` (purpose-built, not the spec's tables) — for the catalog specifically, the spec's shape is adopted rather than reinvented. One adaptation: `documents.root_id` keys against the existing `roots.root_path` (`rootsRepository.ts`, Slice 10) rather than a new generated `trusted_roots.id` — `roots` already plays that role and duplicating it as `trusted_roots` would create two root identities to keep in sync. The spec's `folders`, `headings`, and `index_state` tables are not adopted by this decision; each is deferred to whichever later unit actually needs it (folder-level markdown counts, a persisted heading table, or per-root index status), since `SearchScope` (§8) only needs `allRoots`/`root_id`, not folder scoping. The FTS5 tokenizer (`unicode61 remove_diacritics 2`, matching the spec's own DDL) and the contentless-vs-not choice were settled during Slice 20's build — see that slice's log entry for why contentless didn't work in practice. `bm25()` column weights remain deferred to the unit that implements querying against real data.
- **Search's first query/results pass is one ranked list, no scope, no match highlighting.** _Source: agent, Slice 21 agreement, 2026-09-17._ `search-and-catalog.md` §8's full `SearchRequest`/`SearchResponse`/`QuickOpenRequest` contract (scope filtering across `allRoots`/`root`/`folder`/`currentFile`/`openFiles`, `matchRanges`, separate file/heading/content result kinds) and `quality.md` §4's eight numbered ranking-case tests are not built yet — stated as a scope-down assumption rather than asked, since building the full contract with no working example yet would be the over-build the shape method warns against. `bm25()` column weights: title `10.0`, headings `5.0`, body `1.0` — a first default, not measured against a real corpus.
- **Indexing runs at scan time — wherever `scanRoot()` is already called.** _Source: maintainer, Decision Slice, 2026-09-17._ `scanRoot()` (`src/main/workspace/scan.ts`) currently only walks the tree structure (names/paths), never reading file content; it's already invoked both on add-root and on every `workspace:loadState` launch-restore of a persisted root (`src/main/index.ts`). Indexing at scan time therefore means adding a content-reading step that runs alongside those same two call sites, not folding content-reads into `scanRoot()` itself — keeps the existing tree-walk/content-read separation the codebase already has (`scan.ts` vs `readFile.ts`/`readAsset.ts`). A consequence worth surfacing rather than assuming: because `workspace:loadState` re-scans every persisted root on every launch, this already gives v1 a form of re-indexing on restart with no separate file-watcher trigger needed — inferred from `scanRoot()`'s existing call sites, not a separate answer the maintainer was asked for; flag if that's not the intended behavior.
- **The sidebar is rail-driven: one `sidebarView` state switches its entire body, not just the main pane.** _Source: maintainer, 2026-09-16, overriding the initial "reskin only" framing after seeing it running._ `design-v1.html`'s own 3c artboard keeps the folder tree visible in the sidebar even with Settings active (a nested two-column block inside the main pane instead); the maintainer explicitly wanted Settings to replace the sidebar's folder tree, and any future rail item to behave the same way "from the beginning." `App.tsx`'s `sidebarView: 'folders' | 'settings'` now drives both the sidebar body and the main pane from one value; a future rail item adds a case to that union rather than a new one-off boolean. Recorded as a deliberate departure from the mockup's specific 3c layout, not an error in reading it.

### Constraints

- Windows 11 is the only supported target. _Source: developer._
- Owner must be able to read, review and maintain all code; C#/TypeScript background. _Source: developer._
- `AGENTS.md`: preserve decision identity — record retained / revised / superseded, never renumber or silently rewrite. Do not present proposed features as implemented. _Source: repo instructions, current._
- `AGENTS.md`: no plugin framework in the MVP. _Source: repo instructions, current._ The scaffolding-and-CI half of this constraint is spent — scaffolding was authorized and used in Slice 3, and CI moves into the successor shape's scope.
- Never commit or push unless asked. Show the diff and stop. _Source: skill calibration + `AGENTS.md`._
- `quality.md` §6 performance targets (2s cold start, 10k docs) are an imported claim from the Tauri-era spec, not a measured or user-set budget. _Source: document, unverified — marked `[unverified]` in the document itself, so it stops reading as a limit._ Never measured against the shipped app; carried forward.

### Assumptions

- Real corpora are hundreds to low thousands of Markdown files, not 10k. If far larger, FTS5 and incremental scan get revisited.
- Self-update is not needed for v0.1 — an installer ships; `electron-updater` and signing are deferred.

### Risks

Resolved risks were struck through in place during the run and are recorded in [log.md](log.md); only live ones are carried here.

- **Imported specs read as authority.** They were written for a different project. Anything acted on from them needs a live check first. Still live — `search-and-catalog.md` §8's full contract and `quality.md` §4's eight ranking-case tests remain unbuilt, and both still read as requirements.
- **Large single-document preview is slow.** _Source: developer, 2026-09-15, observed loading `test-docs/big/large.md` (~5.3MB, the search size-cap fixture — see Slice 4)._ Not measured or optimized; not yet known whether this reproduces on a realistic large document (a few hundred KB) or only on that synthetic worst case. If it matters later: cheapest fix is a preview size gate mirroring `maxIndexedFileSizeBytes`, refusing to render past a threshold; more involved is moving markdown parsing off the render thread (Web Worker) and reconsidering sending the whole file content across IPC as one string. Deliberately not acted on — see [log.md](log.md)'s Slice 7 entry.
- **Supply-chain audit findings from `mermaid`'s dependency chain.** _Source: `npm audit`, 2026-09-15, Slice 8; re-confirmed 2026-09-21._ `mermaid` pulls in `chevrotain` → `lodash-es`, which carries high-severity prototype-pollution/code-injection advisories; no fix is available without a breaking `mermaid` downgrade. Together with the pre-existing `extract-zip` finding via `electron`, `npm audit` reports 7 high-severity advisories. Named, not addressed. **This risk changes character on a public repository** — GitHub raises Dependabot alerts against it — and is carried into the successor shape as work, not just a note.

### Open questions

Carried into the successor shape.

1. **Corpus size.** Hundreds-to-low-thousands assumed, never verified against a real corpus. Now bears on whether launch-time re-indexing (see Decisions: indexing runs at scan time) stays acceptable at scale.
2. **Will this be given to other people?** Answered "not yet" 2026-09-19 for the packaging unit, which is why signing and auto-update stayed deferred. **That answer is now changing** — the maintainer intends to make the repository public. Public source is not the same as a distributed signed binary, so the packaging decision may still hold unchanged; the successor shape has to ask the question again rather than inherit the old answer.
3. _(Open, deliberately not being answered.)_ If automated doc triage is built as a separate project, what does MarkScope need to read already-triaged folders — nothing, a convention, or a manifest? Assume **nothing** until there is something real to integrate with. Do not design a seam for this.
