- 2026-09-21 — [Build Slice] 1. Security and correctness hardening. Built, automated-gate-validated, **manual check open** (see Pending validation in `shape.md`).

  **The boundary fix, which is the point of the slice.** New `workspace/trustedRead.ts` joins the two halves of the trusted-root boundary: `isTrustedRoot()` (new, `rootsRepository.ts`) checks the renderer-supplied `rootPath` against the `roots` table, then the existing containment check confines the read to it. `main/index.ts`'s two read handlers now call nothing else. Extracted into its own module rather than left inline in the handlers **specifically so it could be tested** — the handlers register inside `app.whenReady()` and can't be exercised without standing up Electron, which is exactly why the gap survived 21 slices of manual checks.

  **Corrected the comments that asserted the guarantee.** `readFile.ts` and `readAsset.ts` had docstrings claiming they enforced the trusted-root boundary, and the Slice 19 fix removed a renderer-side guard citing that claim. Both now say plainly what they do (contain a read to the root they are _given_) and name the caller as the half that decides whether the root is trusted. The old wording is corrected in place rather than deleted, since the claim is what made the gap invisible.

  **Also in the boundary:** both helpers now `realpath()` root and target before comparing, so a symlink inside a root that resolves outside it fails containment instead of passing on its pre-resolution path. The containment test itself moved to a shared `workspace/rootBoundary.ts` (`isInsideRoot`) so the two files can't drift, and the check is now separator-aware — the previous `rel.startsWith('..')` also rejected a legitimately-contained file named `..config.md`, which is now covered by a test.

  **`window.electron` deleted.** `@electron-toolkit/preload`'s `electronAPI` exposed a generic `ipcRenderer.invoke(channel, ...args)` to the renderer — any channel, any arguments, bypassing the named `api` surface entirely. Nothing in the renderer had ever used it (`git grep window.electron -- src/renderer`: no hits). Removed from `preload/index.ts` and `index.d.ts`, and `npm uninstall @electron-toolkit/preload` dropped the dependency, which nothing else used. Confirmed against the built bundle, not just the source: `out/preload/index.js` now contains exactly one `exposeInMainWorld("api")` and no `electronAPI`. `@electron-toolkit/utils` (main process) is unrelated and stays.

  **Navigation guards.** `will-navigate` in `main/index.ts` now `preventDefault()`s unconditionally — the app never navigates, and the initial load and reloads go through `loadFile`/`loadURL`, which are programmatic and don't raise the event, so no allowlist has to be kept in sync. `App.tsx` also refuses unhandled `dragover`/`drop` at the document level, skipping any event a component already handled (`RootSection`'s reorder zones call `preventDefault` themselves, and React's synthetic handlers run at the root container, so `defaultPrevented` is already set by the time the document listener fires). Main is the backstop; the renderer guard is what makes a dragged file show a "no drop" cursor rather than appear to work.

  **`setWindowOpenHandler` allowlist.** `shell.openExternal` now only sees `http:`/`https:`/`mailto:`, parsed with the `URL` constructor rather than a string prefix test. `PreviewLink` already filtered rendered anchors, but the handler is global and fires for any `window.open`.

  **Four smaller items.** `moveRoot` (`useWorkspaceRoots.ts`) computes the new order off `roots` and calls `setRoots(next)` rather than persisting from inside the updater — StrictMode invokes updaters twice in development, which was double-firing the IPC write on every drop. `upsertDocument` (`catalogRepository.ts`) is wrapped in one transaction, since a failure between the catalog write and the FTS write left a row that lists but never matches a search, and which a later re-scan would not repair (the hash would match and take the fast path). `loadThemeSource` validates what it reads back and `settings:setTheme` validates what it is sent, both feeding `nativeTheme.themeSource`, which throws on anything outside the three values — at launch, before a window exists to report it. The scaffold's `ipcMain.on('ping', () => console.log('pong'))` is gone, with it the only `console.log` in `src/`.

  **Validation (2026-09-21, Windows 11):** `npm run typecheck && npm run lint && npm test` — **151/151 pass, 17 new** (7 `rootBoundary.test.ts`, 5 `trustedRead.test.ts`, 5 added to `rootsRepository.test.ts`). `npm run build` succeeds and the bundled preload was inspected directly, as above. **The regression tests were verified to actually catch the bug**, following Slice 19's precedent: with the `isTrustedRoot` call commented out of both functions in `trustedRead.ts`, 3 of the 5 tests fail — including "refuses a readable file under a root that was never added", which returned the real file contents — while the 2 positive-path tests still pass. That is correct today, because every `rootPath` the renderer holds was handed to it by `workspace:addRoot` or `workspace:loadState`, and it is the same assumption `expanded_folders` and `tabs` already make. - 2026-09-21 — [Pass] 1b. Loading-placeholder flash. Built, automated-gate-validated, **manual check open**.

  **What the pass corrected.** `MainPane.tsx` rendered `Loading <name>…` on `preview.status === 'loading'`, and a local read resolves in about a millisecond, so the text appeared and vanished within a frame or two on every file switch. New `preview/useDelayedFlag.ts` returns true only once a condition has held continuously for a given delay; `MainPane` feeds it the loading status and a new `LOADING_PLACEHOLDER_DELAY_MS = 200` constant. The read itself is untouched — only the feedback about it waits. Nothing renders during the delay, deliberately: the breadcrumb and outline rail have already switched to the incoming file, so holding the previous document would leave the chrome and the content describing different files, which is worse than a blank frame nobody sees. Errors still show immediately.

  **The first implementation was wrong and lint caught it.** It reset the flag with a synchronous `setElapsed(false)` inside the effect, which `react-hooks/set-state-in-effect` rejects as a cascading render — correctly. The comment defending it ("setting a value it already holds is a no-op, so this costs no render") was beside the point: the objection is the extra render cycle on the path where the value _does_ change, not the no-op path. Rewritten to React's documented render-time adjustment (compare against a `previousActive` state, reset during render), which resets before anything is painted rather than painting the stale value and correcting it. Worth recording because the gate caught a design error, not a typo, and because the original comment argued for the wrong thing convincingly enough to have survived a review.

  **Tests.** New `useDelayedFlag.test.ts` (7 cases, fake timers): false while inactive, false immediately on activation, still false one tick before the delay, true at the delay, never true when activation ends first, false again when activation ends, and the delay restarting on re-activation rather than firing straight away. One case in `App.test.tsx` pins the wiring — a rendered document never sits next to a "Loading…" line — which is what would break if the hook were fed the wrong status; the flash itself is not observable at that level.

  **Verified the tests catch the defect**, as with Slice 1: with the hook returning `active` directly (exactly the pre-fix behaviour), 4 of 7 fail. The first draft of the "never becomes true when active ends before the delay" case passed even against the broken hook, because it only asserted the final state, by which point the flag is false either way — its name promised a guard it did not provide. Strengthened with an assertion taken _during_ the short activation, which is where the defect actually lives; it now fails pre-fix along with the other three.

  **Validation (2026-09-21, Windows 11):** `npm run typecheck && npm run lint && npm test` — **159/159 pass, 8 new**. `git diff --check` clean. Manual check pending: switch files rapidly and see no text flicker; open `test-docs/big/large.md` and confirm the placeholder still appears.

- 2026-09-21 — [Pass] Close Pass 1b's manual check, and correct the check itself. Maintainer: **"no loading for small files = ok. though big file shows no loading either."** Point 1 is the Pass's actual goal and it passed. Point 2 was a badly-specified check — it asked for confirmation of something that cannot happen — and chasing it produced the most useful measurement in this shape so far. No code changed by this Pass.

  **The measurement.** `test-docs/big/large.md` is present (5.06MB) and reads in **4.2ms cold, 2.8ms warm**. Parsing it to mdast with the same `unified`/`remark-parse`/`remark-gfm` combination the app uses takes **9,238ms**. `preview.status` is `loading` only for the read, so the placeholder covers 4ms and misses 9.2 seconds; by the time the expensive work starts, the status is already `ready`. The placeholder was therefore never going to appear for this file, before or after Pass 1b. What the delay actually revealed is that the placeholder only ever reached the screen _because_ it was flashing on fast reads — it had no reachable job on local disk.

  **Consequences worth being precise about.** Pass 1b is correct and stays: it did what it was for, and the delayed placeholder is still the right shape for a genuinely slow read, which this app can hit because it takes arbitrary folders and a network-mounted root is not a hypothetical. But on local disk it will essentially never render, and the docs should not imply otherwise. Deleting it instead was considered and rejected: the failure mode without it is a blank pane with no explanation, and the cost of keeping it is one small hook.

  **The Risk is now measured.** The MVP shape carried "Large single-document preview is slow" with "Not measured or optimized" and an open question about whether it reproduced on realistic documents or only on the synthetic worst case. It is now measured, and the cost is located: not the read, not IPC — the markdown parse, twice per open (`preview/headings.ts` for the outline, then react-markdown's own parse for the render), before React builds the tree. That also puts a number on the MVP shape's Slice 16 decision, which chose re-parsing over DOM-scraping and recorded the cost as "not measured, and not expected to matter until it's shown to." At 5MB it is shown to; at the hundreds-of-KB sizes real corpora hold, it still is not.

  **Not fixed here, deliberately.** A preview size gate mirroring `maxIndexedFileSizeBytes` is the cheap fix and is now a candidate slice with a real number behind it. It is not a blocker to going public: it bites on a synthetic 5MB fixture, not on the documents this app is for. Sequencing it against the release is the maintainer's call.

- 2026-09-22 — [Build Slice] 5. CI and the distribution decision. **Narrowed mid-unit**, and the remainder split off rather than built — see below. Resolves Open questions 2 and 4.

  **Narrowed, and why.** Slice 5 was scoped as "CI, merge and publish". Two thirds of that is not buildable from here: the merge needs commits that do not exist yet (five units are staged, none committed), and publishing is a push plus an irreversible visibility change the maintainer explicitly reserved. What remained is CI and the distribution decision. The rest is now a written checklist in `shape.md` rather than a slice — it is a sequence of maintainer actions, not work, and holding it in the slice list would imply the agent could do it.

  **`.github/workflows/ci.yml`** runs the Working Agreement's own gate — typecheck, lint, test — on `windows-latest`, plus `npm run build`. Windows-only because that is the only supported target (ADR-0016) and because `better-sqlite3` resolves a `win32-x64` prebuild; a green run on Linux would verify a platform nobody ships. `npm ci` rather than `npm install`, so lockfile drift fails the build — the mechanical version of the Working Agreement's rule that dependency versions never come from memory. Confirmed beforehand that no test imports `electron`, so the gate needs no Electron binary even though the install still fetches one.

  Two deliberate omissions, both documented in the file: `npm audit` is **not** a step (7 known unfixable advisories would make it permanently red, and a gate that is red on purpose teaches people to ignore it), and `better-sqlite3`'s install script stays blocked exactly as it does locally.

  `npm run build` is in CI despite not being in the local gate, because it covers the one failure class the gate provably misses: a main-process module that typechecks and unit-tests clean but breaks once electron-vite bundles it. That has happened here once — the `unwrapEsm` problem in `extractHeadingText.ts`, caught only by running the app.

  **Distribution: build from source only.** _Source: maintainer, 2026-09-22, answering the fork directly._ v0.1 publishes no binary anywhere — no release, signed or unsigned. `npm run dist` still works and packaging is untouched; the decision is about distribution, not packaging. Recorded as a dated addendum on [ADR-0009](../../adr/0009-github-releases-for-distribution-and-updates.md), which this narrows for the third time (updater artifacts dropped 2026-09-13, self-update deferred, now no artifact at all). The reasoning worth keeping: an unsigned installer asks a stranger to click through a publisher warning on the word of a repository they have just met, and v0.1's audience is someone evaluating how it was built rather than someone who needs it installed. Reversing it needs a release, not an ADR; reintroducing signing or auto-update needs an ADR, because both were rejected on their own grounds.

  Also closed Open question 4, inherited from the MVP shape as "will this be given to other people?" — the distinction it suspected turned out to be exactly right: the source is, the binary is not, and the no-signing decision stands on its own grounds rather than by inheritance.
